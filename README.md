## Run the game locally

This is the shortest way to start the complete game on Windows. You need [Node.js 22.12 or newer](https://nodejs.org/), [Rust](https://rustup.rs/), and the [SpacetimeDB CLI](https://spacetimedb.com/) installed first. The setup commands below use PowerShell.

1. Open PowerShell in this project folder, download the project's submodule and install its packages:

```powershell
git submodule update --init --recursive
corepack enable
pnpm install
rustup target add wasm32-unknown-unknown
```

2. The first time you run the game, start the database and client together, leave them running, then publish the backend from a second PowerShell window:

```powershell
pnpm run dev
```

```powershell
pnpm run deploy:local
```

3. Open [http://localhost:5173/](http://localhost:5173/).

`pnpm run dev` starts SpacetimeDB at `http://localhost:3000` and the Vite client at `http://localhost:5173`, then stops both processes it started when you press Ctrl+C. If SpacetimeDB is already running, the command reuses it and leaves it running on shutdown. `npm run dev` works the same way. On later visits, this single command is all you need. Rerun `pnpm run deploy:local` only after backend, schema, or balance changes.

**Selo Empire** is a real-time medieval city-building and settlement simulation on a procedural 3D landscape. On a fresh game, choose map size, topography, hydrology, forest density, regional resource abundance and variety, and world seed before generation begins. Draw dirt road networks across rolling hills, pine forests, and winding rivers — wooden bridges and graded ramps appear automatically when a path crosses water. Place production buildings to harvest timber, stone, game, berries, and fish; connect wells and depots along those roads; then lay out residence zones so settlers move in over time. Homes need firewood, water, and food: physical haulers stock Marketplace stalls while wells refill from local groundwater, then connected homes receive those provisions through abstract availability instead of a cart visiting every door. Staffed Granaries and Village Storehouses still move real stock into the market. Plant backyard gardens for household consumption, cross-household exchange, savings, and a physically collected local tax; use a staffed Trading Post for general regional trade, while a frontier monastery has a narrow charter to export its own estate surplus. A [SpacetimeDB](https://spacetimedb.com/) Rust module runs the authoritative economy simulation; the client renders replicated state in real time.

Food is physical and keeps its identity throughout the economy: bakeries make bread, hunters supply meat, fishing camps land fish, foragers gather berries and mushrooms, households grow fruit, vegetables, and eggs, and livestock or specialty sites produce milk, cheese, cured meat, smoked fish, grapes, and honey. “Food” is only the meal-equivalent total used by household demand and the HUD summary. Clicking that HUD total opens the stored, carted, household, and surplus breakdown for every actual food commodity.

## Recent updates (July 2026)

- **Authoritative rural commute productivity** — the household routes shown for exposed lumber, stone, mineral, clay, and charcoal crews now affect the economy instead of remaining presentation-only. Once per calendar day, after labor rotation, the server matches staffed workplaces to healthy household and founders'-camp labor by the same road-preferred travel order and stores only a derived shift fraction; production reads that scalar without pathfinding in the hot loop. Long round trips therefore slow timber, stone, iron, salt, clay, and charcoal cycles, making nearby housing and road geometry real industrial choices. A completed, fire-safe linked overnight camp restores its parent yard to a full productive shift immediately, while fire or demolition immediately exposes the cached household commute again. Existing saves default to full output until their first daily review, and the worksite inspector labels the authoritative percentage.
- **Commute-aware work crews and physical overnight camps** — visible workers claim households settlement-wide by real road travel, leave early enough to reach a distant shift, and set out for home soon enough to preserve useful rest. Dawn and dusk never reverse a journey already under way, and a worker who reaches home after dawn still takes a guaranteed six-hour rest. Exposed extraction sites—lumber mills, Mining Pits, Quarries, and charcoal yards—can plan one nearby overnight camp from their own inspector card. It is a real 14-timber/3-stone building: placement must remain within 34 m of its parent, materials are reserved and brought by haulers, builders raise it, fire can disable it, and demolition leaves ordinary reclamation. Only after completion do its two canvas tents and live campfire replace the household commute. Reforester huts, woodcutters' lodges, hunters' halls, foragers' sheds, fishing camps, pastoral farmsteads, and swineherds instead provide canonical built-in crew bunks automatically; barns, apiaries, vineyards, and urban, civic, and processing jobs remain daily commutes. Inspectors report the measured route, effective shift, lodging rule, and linked camp state so distant employment stays a legible settlement choice.
- **Physically watered village forges** — smithies no longer turn ore and charcoal into finished ironwork as a dry, isolated recipe. Every forging cycle now consumes one unit from a visible coopered quench tub, and only completed road-linked wells can supply the workshop by physical cart after fire calls and household needs are covered. Wells are unstaffed infrastructure: the nearest suitable source claims an unassigned hauler when demand is live. Lean, Balanced, Deep, and Fill stock policies stage one, two, or three forging cycles of water alongside iron and charcoal; input specialization, lowest stock ratio, road distance, and stable order decide which thirsty workshop wins a contested well cart. A forge without an operational well on its road branch contributes no sustained ironwork capacity, while its inspector, well ledger, Town Hall material chain, and declining tub surface expose the exact shortage.
- **Settlement-scale household wells** — an excellent aquifer in fair weather sustains at most fifty fully occupied four-person homes; poorer groundwater and drought reduce that yield, preserving pressure to site additional wells as the settlement grows. The well inspector separates the number of homes currently connected from sustainable household capacity, so a small new road branch no longer reads like a two-home hard limit.
- **Physically puddled pottery clay** — potters no longer fire dry clay and fuel as a self-contained recipe. Every kiln cycle now consumes carted well water to puddle and clean the clay before forming, and a kiln without a completed well on its road branch contributes no sustained pottery capacity. The existing workshop stock policy stages one, two, or three water cycles beside clay and firewood; fires and household water remain ahead of industry, then lowest runway, road distance, and stable order decide which kiln receives a free hauler's well cart. Kiln, well, Town Hall, build-card, and HUD guidance expose the dependency, while a stone-lined puddling pit visibly fills and empties with onsite water.
- **Climate-bound charcoal clamps** — charcoal output now depends on the condition of the billet charge instead of running at an identical rate through every season. Wet spring and snowbound winter reduce authoritative clamp cycles to 80%, while drought-dried wood raises them to 110% at the cost of coinciding with the yard's highest fire danger. The same generated policy drives actual firewood consumption and charcoal output, Town Hall and workshop forecasts, input runway, next-day warnings, inspector explanations, and a bounded low-poly smoke plume, turning autumn charcoal reserves and isolated hot-yard placement into one connected planning decision without adding save state.

- **Unified geological extraction** — stone, iron, salt, and clay now share one mental model. Every node has a finite surface reserve worked by a Mining Pit placed nearby; every rich node also has a separate non-depleting underground source worked by a timber-supported Quarry centered on the node. Tooltips use the same surface count and underground-source wording across all four resources. The old Stonecutter's Camp, Mineral Mine, and Clay Pit cards are removed, while their internal identifiers remain as save-compatibility shims.
- **Player-governed extraction yards** — Mining Pits and Quarries share Lean, Balanced, Deep, and Fill yard ceilings for their physical stone, iron, salt, or clay output. Consumer carts may draw below the selected ceiling and restart work; lowering it never deletes stock, but it preserves finite ground, stops deep-support and tool wear, and lets Town Hall production stewardship recall surplus diggers while retaining a needed dispatcher. Every inspector shows current stock, exact headroom, and the four controls. Existing sites default to Fill through the established production-target field, so saves retain former behavior without migration.
- **Live regional import caravans** — paid grain, iron, salt, fittings, provender, water casks, and other imports enter from a deterministic Adriatic-facing map edge on a visible commodity-specific cart. Manual lots unload at their Trading Post before local logistics continue; emergency household and parish-relief orders pass through that post's branch and continue to the exact home that paid for or received them. The empty merchant cart must leave before that post can contract another regional load, so map size, road placement, seasonal pace, trader staffing, and a second post change sustained capacity.
- **Two-way physical regional exports** — staged timber, stone, food, firewood, pottery, barter lots, ale, honey, wine, and cloth normally leave through a Trading Post. A foreign merchant carries each load out through the site's road branch, exchanges only cargo that survives spoilage or a raid, then returns with physical gold or barter goods. The monastery is the one narrow exception: routine mixed-estate surplus may leave directly under its charter and returns as the house's gold-in/gold-out proceeds. The configured export duty is reserved from returned gold for civic collection, while the net stays onsite for automatic estate reinvestment. Player-laid monastery vineyards remain a deliberate physical chain: monks press their grapes at the separate vintner and surplus wine enters town storage. One post cannot overlap regional import and export contracts; local Marketplace stall carts remain independent.
- **Smith-dressed watermill stones and bread-chain ironwork** — grain watermills now join the same physical forge economy as farms, forestry, quarrying, clay digging, and firewood. A mill with dressing hammers and sound iron fittings grinds 20% faster, multiplying rather than replacing spring rain, drought, or frost river power; each completed milling cycle wears 0.25 ironwork, while an empty rack retains baseline output. Smithies cart a three-cycle working buffer by road and remaining runway, and the watermill model shows four declining tool bundles beside its grain and flour stores. Individual mill buffers, road-branch bread capacity, grain draw, output-room timing, and Town Hall ironwork demand all use each mill's actual tool condition. Mining Pits likewise forecast only the tool wear their completed work can incur. Existing saves need no migration and begin with an optional empty mill rack.
- **Physical iron farm tools and seasonal labor compression** — crop farmsteads now join the same smith-forged ironwork economy as forestry, quarrying, clay digging, and firewood. A stocked rack of wooden ploughs with maintained iron shares, hoes, sickles, and scythes makes real ploughing, sowing, and harvesting progress 20% faster; empty racks retain baseline work so an import or smithy failure cannot silently erase a crop. Wear is proportional to completed field work at 0.05 ironwork per baseline worker-day of work, not to ticks or parcel count, so dividing one field cannot evade the cost and workers away with a cart consume nothing. Smithies physically cart a three-stage working buffer by remaining runway and road order, while the farmstead model shows four declining tool bundles. Farmstead, field, and Town Hall inspectors reconcile current pace, onsite and inbound stock, planned wear, whole-season reserve targets, and spring, autumn, or September labor coverage; dormant growing fields drop out of current daily smithy demand. Existing saves need no migration and begin with optional empty racks.
- **Smith-maintained winter-fuel axes** — the existing iron, charcoal, smithy, and firewood chains now meet at every staffed woodcutter's lodge. A lodge with replacement ironwork processes timber 20% faster and wears 0.25 ironwork only after a completed firewood cycle; an empty rack retains baseline output so a smithy shortage creates a meaningful winter-efficiency penalty rather than a settlement-ending hard stop. Every assigned lodge worker processes timber continuously, while an unassigned hauler carries finished firewood and inputs without reducing lodge output. Town Hall firewood capacity, timber draw, tool demand, road coverage, and smithy surplus use the same production-only roster model.
- **Climate-bound cured reserves and player-directed centralization** — cured provisions now follow the same deterministic seasonal environment as crops, roads, and fresh food instead of aging at one year-round rate. Spring damp and autumn humidity modestly raise loss, ordinary summer warmth raises it further, drought is the harshest condition, and winter cold halves ambient aging before each store's protection; the four normal seasons retain the previous annual-average balance. The authority and client apply the current rate to smokehouse lofts, granaries, markets, ordinary holdings, household cupboards, handcarts, and legacy reserves, while next-dawn outlooks, inspectors, food runways, and thirty-day reserve recipes expose the same pressure. The granary's existing intake switch now governs both fresh and cured surplus: disabling it leaves cured stock in the better smokehouse loft, while enabling it spends producer haulage and accepts slightly faster aging in exchange for central redistribution. This connects climate, road layout, cart contention, storage quality, and winter planning without a new inventory or save field.
- **Finite cured-food reserves** — salted and smoked provisions now age slowly in every physical store instead of becoming a permanent calorie bank. The generated balance gives smokehouse drying lofts the best retention, followed by granaries, monasteries, and markets; ordinary holdings, household cupboards, legacy reserves, and exposed handcarts lose quality faster. The authority decays building, cart, treasury-compatibility, and residence stock continuously, including during rest periods, while the client uses the same factors for household runway, road-branch warnings, and Town Hall loss hotspots. Thirty-day fallback targets now include the small quantity that will age while consumed, and production-day, salt, firewood, and pottery forecasts include losses while the reserve is being built. This keeps cured food useful for months without rewarding indefinite hoarding, adds no save fields or parallel inventory, and retains a single linear diagnostics pass at roughly 68 ms for 100,000 granaries.
- **Granary-centered cured-food reserves** — preserved provisions move physically from smokehouses and pastoral holdings into road-linked Granaries, then staffed food stalls place that stock in the Marketplace. Connected tier-four homes receive the real stall inventory through abstract availability, nearest first when it is scarce; Granary workers no longer spend their day carting three-unit ration loads to individual doors. Critical grain, military provisions, brewery barley, preservation, and institutional routes remain physical. Tier-four promotion still requires a sustainable producer plus the appropriate market service, so an empty warehouse cannot fake prosperity.
- **Stock-aware meal and bread planning** — every settlement forecast now follows the same calorie-neutral meal allocation as the authoritative household simulation. A prosperous home first schedules its current seasonal cured ration, subtracts only the amount physically present in that cupboard from today's fresh-food need, and falls back to the gross meal demand when the cured stock runs out. Town Hall bread capacity, household buffers, Sabbath readiness, full-housing growth, residence meal mix, HUD demand, and road-branch runways therefore stop charging prosperous residents for full fresh meals plus preserved food at the same time. Fresh-food runway spends only finite fire-accessible cured stores, at the bounded seasonal rate, before returning to gross demand; disconnected and fire-quarantined smokehouse stock cannot extend a branch. The settlement scan keeps the per-home calculation allocation-free, adds no save fields, and preserves the separate thirty-day all-preserved emergency reserve as a deliberate worst-case target.
- **Calorie-neutral seasonal preserved rations** — prosperous households now actually rotate cured provisions through their meals instead of letting one morsel satisfy the preserved-food expectation forever. The allocator replaces part of the same fresh-food meal rather than charging a second calorie demand, then draws deeper from preserved stock only when fresh food is short. Spring uses 0.75× of the annual-average ration, summer 0.5×, autumn 1×, and winter 1.75×; the four equal seasons still average exactly 1×, while winter becomes the design peak for promotion capacity and summer becomes the natural stockpiling window. Household runway, Sabbath buffers, Town Hall capacity, growth forecasts, smokehouse inputs, salt orders, pottery vessels, and the thirty-day emergency reserve all read the same policy. The authoritative hot path is allocation-free and resolves one million meals in roughly 60 ms under the native debug benchmark.
- **Road-matched winter preservation reserve** — the Town Hall now turns tier-four households' emergency preserved-food fallback into a concrete thirty-day preparation target instead of presenting it as ordinary daily consumption. The ledger matches each occupied tier-four home to preserved stock and incoming carts on its own road branch, excludes fire-quarantined stores, identifies the weakest branch, and forecasts completion from staffed same-branch smokehouses. Every missing unit resolves back into exact fresh food, firewood, salt, and pottery-vessel requirements; stored and inbound salt is counted first, then forecast output from staffed physical salt mines on the same road branch, with ordinary seams capped by their remaining geological reserve. Only the residual shortfall becomes Adriatic import lots and current-rate gold exposure. The planner is a linear, read-only view of the existing physical economy, adds no save fields, and makes mine placement, kiln priority, broker funding, cart routing, workshop placement, and autumn stockpiling part of one visible decision.
- **Physical pottery chain, abstract household availability** — tier-four households require a slow replacement flow of cooking, serving, and storage vessels. Kilns physically supply staffed Storehouses, Storehouses cart wares to Marketplace goods stalls, and connected tier-four homes draw from that real stall stock without individual pottery carts. Smokehouse packing buffers and regional export remain physical competing uses. Tier-four upgrades still require an operational pottery chain and staffed goods-stall access.
- **Player-directed pottery cart priority** — every potter kiln can keep the save-compatible household-wares-first order or stage preservation vessels first. Homes-first protects prosperous cupboards before serving smokehouses; preservation-first protects salted winter-food throughput before replacing household breakage. Either mode immediately falls through when its first local duty has no reachable shortage, and export always remains third, so a nearby broker cannot consume the kiln's one physical cart while either local chain is exposed. The kiln inspector states the exact order and previews the destination selected by that same policy.

- **Deferred settlement ledgers** — the complete inspector and Town Hall reporting graph now leaves the initial application chunk and downloads through the existing settlement-presentation boundary while terrain generation is already under way. The initial production entry fell from 1.735 MB to 990 KB raw and from 493 KB to 310 KB gzip without removing any economic forecast, model, or interaction. A production-build regression test proves the inspector stays outside the entry chunk and enforces 1.10 MB raw / 350 KB gzip startup budgets as future systems grow.

- **Readable settlement Approval** — the top command bar keeps a persistent 0–100 Approval score, named tier, and short-lived trend arrow in view. Clicking it opens a compact ledger of the strongest supporting factors, the needs that deserve attention, and the growth, taxation, residence-promotion, and cohesion effects already enforced by the simulation. The score is derived client-side from authoritative provisions, welfare, hunger, illness, sustained household service pressure, cohesion, winter warmth, burials, fires, fatigue, and active frontier danger, so it adds no duplicate save state or competing simulation authority.
- **Persistent homes and actionable settlement welfare** — homes never become abandoned or decay from vacancy. Death simply frees reusable capacity for future settlers. A three-day unmet-need grace period is followed by approval pressure; six days blocks tier promotion, while household work, market activity, and assessed tax continue at their normal rates. Hunger, malnutrition, sickness, remedies, service pressure, mortality, burial carts, grave capacity, and reusable housing resolve into one shared Town Hall summary, while the HUD appears only for real watch or critical conditions. The summary is folded into the existing provisioning residence pass rather than adding another snapshot scan.
- **Household-first fuel economy** — staffed Village Storehouses physically stock Marketplace goods stalls, which allocate firewood instantly to connected homes; nearby households receive scarce supply first and no worker is reserved for the last mile. Remaining source stock can still travel physically to bakeries, breweries, smokehouses, charcoal clamps, or pottery kilns. Industrial dispatch is source-side and deterministic: staffed workshops compete by lowest recipe-cycle runway, road distance, and stable identity, so table update order can no longer decide which production chain stays hot. An idle workshop cannot sequester communal fuel, while each processor's output-stock target controls whether it stages one, two, or three firewood cycles. Lodge and storehouse inspectors preview the next industrial claim and active destination. The Town Hall separates cupboards, market stock, hot-workshop buffers, live carts, inactive stock, and fire-quarantined stores; it also compares full-winter hearth demand plus installed industrial burn against sustainable staffed-lodge output and timber draw on every road branch. Existing saves need no migration.

- **Legible industrial fire planning** — the severe accident risk already carried by charcoal clamps and smokehouses, and the elevated risk at smithies, pottery kilns, fuel-heavy workshops, barns, breweries, and granaries, now becomes a layout decision before construction instead of a hidden coefficient. One generated balance table feeds both the Rust ignition authority and client forecast. Placement and inspector readouts report current stored-fuel amplification, operational buildings and occupied homes exposed within spread range, the selected well route, and estimated first-bucket arrival without drawing an exact radius in the world. A busy nearest well now yields the emergency to a farther ready responder instead of blocking the entire response. This adds no save field or periodic settlement scan, and the derived planning pass remains near 14 ms for 100,000 buildings.
- **Directional, uncertain raid warnings** — the exact incursion schedule is no longer exposed as a guaranteed HUD timetable. Ordinary scouts and travelers may miss an approach, although larger raiding parties are progressively harder to conceal. A staffed watchtower reliably detects only the actual map-edge lane reached by its effective sight radius: one lookout has a smaller detection footprint, two have the full radius, an outward tower provides more lead time, and a tower on the wrong side of the map provides none. The authority persists the planned side so a reported northern approach cannot become an eastern spawn if stored wealth shifts before contact. A successful report raises a toast with source, direction, party size, and an approximate countdown; an undetected raid instead raises an immediate contact alarm. Likely-target markers remain hidden until a real report or physical contact.
- **Committed cart round trips** — work hours and an observed Sabbath still block every new ordinary-cart departure, but a crew already on the road now finishes its outbound leg, unloads, and returns home instead of freezing at 20:00 and resuming in place the next morning. Fire response retains its emergency exception, while a live raid still recalls exposed outbound carts and lets returning carts complete their retreat.
- **Physical fire displacement** — a fire-disabled workplace no longer leaves its visible crew forging, harvesting, drilling, or standing inside the burning site while the authoritative economy is paused. The same rostered people put away their tools, evacuate over the real local route to their household or founders' camp, remain inspectable as fire-displaced, and commute back only after recovery; their labor assignment is not silently freed. Residents who are actually home leave the house for deterministic assembly places beyond its footprint, while household members already working at a safe site keep producing so presentation does not invent a server-side labor loss. During a frontier alarm, a burned guard post no longer grants defense-duty immunity and a burned refuge cannot receive a rally. Fire-disabled homes immediately lose ordinary hearth smoke and window light, and their residents physically return after recovery. The routine adds no save fields and remains bounded by the existing 1,024-agent crowd ceiling.
- **Player-directed loom inputs and fibre routes** — every weaver can now use the legacy automatic recipe choice, prefer a ready wool cycle, or prefer ready flax plus hauled water. Among active looms, sheep-holding and farmstead carts replenish a matching specialization before the neutral Auto pool and the opposite fallback, while covered working buffers return to nearest-route overflow. Flax-first looms with fibre physically staged also enter the well's household-first industrial queue ahead of neutral workshops, while wool-first looms yield contested water; this replaces update-order-biased target pulls with the same one-pass source-side arbitration used by bakeries and brewhouses. The alternate recipe remains a production fallback so a stocked workshop does not idle, and authoritative dispatch, client route previews, production, Town Hall input-runway forecasts, well and workshop inspectors share the policy. Wool-first saves planned flax for later; flax-first turns field fibre and well/cart capacity into cloth while preserving the annual fleece clip. Existing workshops default to automatic selection. Fibre, industrial-water, inter-building cloth, and export hauls remain physical; household water and market-cloth availability are abstract after reaching their distribution point.
- **Inspectable, fordable live combat** — every replicated raider and defender can now be selected in the ordinary person inspector to read their current objective, health, equipment, readiness, captured stores, and exact activity instead of inferring the battle from an aggregate alert. Combat visuals use the existing road-surface sampler while taking a bridge, so fighters no longer appear below its deck. Rivers remain intentionally fordable cross-country terrain for both sides, reflecting the settlement fantasy of shallow Gorski Kotar and Kupa-valley crossings: a river or delta cannot become an invulnerability wall, while roads and bridges retain their faster coordinated-route advantage.
- **Audible physical melee** — close inspection of a live fight now carries sparse, generated polearm impacts, shield contact, equipment movement, and nonverbal human exertion from the combatants' actual map positions. Approaching, retreating, downed, and ordinary-duty agents remain silent; distance attenuation and the strategic-zoom cutoff keep the settlement soundscape readable, while pausing or ending the engagement stops in-flight sounds immediately. One source per active raider, a twelve-source ceiling, shared one-shot pools, and global cadence limits keep the pass bounded even when many defenders answer the alarm.
- **Physical raid contact and exact loot** — every building, cottage, treasury seat, and refuge now receives a deterministic exterior assault point on the raider's approach side instead of drawing attackers through its model center. The authority derives building envelopes from the shared placement catalogue, uses the authored cottage radius, keeps moving carts on their live position and broader interception radius, and ends cached incursion routes at the same physical contact. Raiders visibly strike stationary holdings throughout forced entry, while moving-cart plunder remains a rummaging action and guards may leave roads to intercept anywhere. When several raiders share a target, complementary carrier shares now reproduce the declared loss budget exactly if all succeed instead of compounding below it; only agents that actually finish contact carry anything away. Interrupted or reconnected wounded guards also return their issued polearm to the rack only after physically reaching their guardhouse.
- **Authoritative on-map frontier combat** — due incursions now spawn a bounded party of replicated raiders at a deterministic map edge instead of applying an off-map loss roll. Each raider owns a live position, target, health, combat state, and carried-loot bundle; each responding guard is backed by one armed slot in an actual guardhouse roster and temporarily replaces that worker's ordinary crowd figure. Roads are a faster preferred leg, never rails: guards and raiders cut across country to intercept, chase carts, fight, reach an active attack, or answer an unlinked holding. Both sides physically close distance and exchange melee damage, using the villagers' authored movement and weapon-swing animation with the existing audited CC0 spear. A raider must reach the exact building, home, treasury seat, or moving cart and spend four local seconds looting before its authoritative stock can change; arson is possible only after that contact, and carts cannot be burned as structures. Stolen commodities travel back out on the raider, while an intercepted carrier drops the exact bundle into a recoverable map stockpile. Capable raiders who are advancing, fighting, looting, or physically retreating directly govern refuge rally and the settlement-wide emergency stop. New ordinary-cart departures cease, carts caught outbound or unloading reverse along their physical route with the same crew and exposed cargo, already-returning carts keep moving, and fire responders continue; pursuing raiders still chase the cart's live position and can plunder only after contact. If a pursued cart reaches home first, the same live pursuit transfers to its receiving store before the cart row clears; its loss fraction is rescaled to the remaining cart value so arrival cannot despawn an attacker or expose an unrelated warehouse windfall. Combatants and carts advance on the same five-heartbeat physical cadence at the selected game speed instead of making battles wait on sparse calendar/economy steps. Once the last hostile escapes or falls, ordinary work, carts, migration, and household settlement resume while guards continue their visible return and recovery. Survivors must physically escape and guards must walk home before the final report is recorded. Peaceful worlds clear the combat lifecycle entirely, simultaneous multiplayer raids are owner-isolated, party size is capped at twelve, and the hot movement/combat policy remains deterministic and benchmarked.
- **Persistent guard casualties** — a guard downed in physical combat no longer disappears into an abstract result or returns to duty at the next update. That same replicated roster agent remains on the battlefield, limps back to its source guardhouse after the raiders are gone, and recuperates visibly for three to five in-game days; a well-supplied, paid company recovers faster. Its exact roster slot cannot muster again, be released into another workplace, or be erased by demolishing or reconstructing the guardhouse. Wounded guards continue to consume company provisions and wages, the authoritative district forecast subtracts them, and the HUD plus guardhouse ledger distinguish fighters in the field, evacuation, on-site recovery, fit strength, and remaining recovery time. Recovery reuses the existing combat-agent row and state tick, so old saves need no migration or parallel casualty table.
- **Player-directed company muster posts** — a completed guardhouse can now keep the save-compatible nearest-watch order or be bound to one chosen completed watchtower. An explicit order lets a rear company reinforce a threatened district without rebuilding the post, but its real road length and seasonal travel penalty still reduce timely strength; if that watch is unstaffed, burning, or cut off, the company waits rather than silently teleporting to a safer district. The guardhouse ledger previews every post from one batched road tree, exposes the active order and failure state, and the selected route, raid forecast, visible spear muster, and authoritative raid outcome all consume the same assignment. Demolishing the post safely returns its companies to automatic duty. One additive zero-default building field preserves existing saves and adds no new unit, commodity, or per-tick scan.
- **Visible road-linked guard musters** — when raiders are reported during the April–October campaign season, every equipped guardhouse worker now leaves ordinary drill, follows the same road-linked watch claim used by the raid forecast, and forms a deterministic spear line clear of the tower ladder. Several companies answering one watch extend the formation instead of overlapping; watchmen remain on the gallery, while unarmed, disconnected, or fire-disabled companies do not falsely appear in the response. Guards return to their guardhouse when the alert clears. The forecast and crowd presentation reuse one batched muster plan—one road tree per company—so no route is solved twice, and the change adds no save field or new asset beyond the existing audited CC0 hand-rigged spear.
- **Visible civilian refuge rallies** — once raiders are reported during the April–October campaign season, rendered members of every assigned household leave ordinary routines, follow roads and yards to their claimed palisaded refuge, pass through its open gate, and occupy one of 32 deterministic places inside. They return home—and workers resume their normal commute—when the alert clears; winter pauses and peaceful worlds never trigger a rally, while defense workers remain on duty rather than taking civilian places. The raid forecast and crowd presentation reuse one capacity assignment instead of sorting the settlement twice, add no save state, and make overlap, overcrowding, fire loss, and exposed homes readable directly on the map.
- **Capacity-bound civilian refuges** — each compact palisaded enclosure now holds at most 32 residents instead of sheltering an unlimited village. Warned families claim places as whole households at their nearest active refuge, then try an overlapping second enclosure when the first is full; anyone who still lacks room remains exposed, and a burning refuge removes its capacity immediately. ## Setting & visual direction

**Gorski Kotar, Croatia — circa 1500–1600.** The default sandbox is a wet, wooded highland in the Dinaric Alps: beech–fir valleys, karst ridges, limestone hamlets, and seasonal trade with Kvarner. Regional market goods, forest species, and building materials all lean into that slice of Croatian history. You are free to retarget the game to another region or era — treat this as a starting point, not a hard constraint.

**Build menu cards** use a **Croatian naive art** style — folk painting with flat color, bold outlines, and charming asymmetry. Examples live in `public/assets/ui/build-menu/`.

**3D buildings and residences** follow the shared [building visual language](docs/design/building-visual-language.md): grounded Gorski vernacular, limestone-and-timber construction, and silhouettes readable at settlement zoom. The chapel mesh is the reference implementation.

**Generating new assets?** Before asking an LLM or agent to create buildings, menu illustrations, or textures, point it at `docs/design/building-visual-language.md` and the existing art under `public/assets/` so output stays consistent. To shift the whole aesthetic — different country, period, or illustration style — update that document first (or ask your agent orchestrator to do that), then regenerate art and meshes against the new brief.

## Features

### Road building

- Interactive point-by-point road drawing projected onto a 3D terrain heightfield.
- Terrain projection so roads follow hills, slopes, and ground variation.
- Snapping to existing road nodes and road segments.
- Automatic edge splitting when new roads connect to existing segments.
- Wheel-adjusted curvature per segment (`Ctrl + scroll`).
- Junction classification for endpoints, bends, T-junctions, cross-junctions, and complex junctions.
- Junction and endpoint cap meshes that blend road ribbons into clean intersections.
- Textured medieval dirt road materials with irregular blended shoulders.
- Live road preview while drawing, plus selection and delete with confirmation popup.
- Undo last placed point, undo last committed change, redo (`Ctrl+Y`), and full draft cancel.
- Terrain road-wear blending that tints grass to packed dirt along committed road corridors.
- Automatic river bridge generation when a road crosses water — graded approach ramps, elevated deck, and instanced support posts.
- Wood-log bridge deck material blended onto the road ribbon via a per-vertex `bridgeBlend` attribute.
- Bridge preview tint while drawing, plus placement validation that rejects spans wider than the max bridge length.
- Rock collision checks that block roads through scattered forest and river-shore boulders.
- Road-network connectivity for gameplay — buildings and residences must share a road branch for access, inter-building hauling, Marketplace availability, and well service.

### Economy & settlement

- **Frontier security** — contested worlds begin generating pressure after the settlement reaches eight people. April–October incursions choose a bounded pressure-scaled set of the richest exposed stores, treasury reserves, moving carts, and households, then materialize people at the map edge. Raiders can steal only from a holding they physically reach and loot, can ignite at most one contacted structure, carry the removed goods during their retreat, and drop that exact bundle for recovery when a guard downs them. Armed, supplied guardhouse workers answer their assigned staffed watch district as replicated defenders, physically intercept attackers, exchange melee damage, and return to their post after surviving raiders escape or fall. The ordinary well, bucket-cart, fire-spread, damage, repair, and reconstruction systems handle any resulting fire. Watch coverage provides warning and a lower exposed-loss share rather than immunity; company placement, weapons, provisions, roads, and player-selected muster posts determine whether real guards arrive in time. Each frontier report names the current likely targets, bounded amber-to-red world markers identify them as pressure rises, and the HUD reports live combatants and downed agents. Periodic forecasts still build one coarse-cell watch index and classify candidates in one holding pass, while the live party is capped to keep per-tick combat bounded. Peaceful worlds remain fully raid-free and contain no combat agents.
- **Raid-vulnerable reconstruction stores** — beginning fire recovery no longer makes retained food, textiles, armaments, or money disappear from the frontier economy. Stock-bearing worksites remain valid raid targets and contribute to warning coverage until their goods are moved or lost, while empty new construction sites remain irrelevant and unfinished watchtowers or guardhouses provide no defense. The rule derives entirely from existing building state, so old saves need no migration.
- **Frontier watchtower** — a road-linked hillside defense staffed by up to two watchmen drawn from real settlement households. Both the guardhouse and Town Hall forecast the next day's funded wages. Each carpenter can hold 0, 2, 6, 12, or 24 finished polearms; a zero target preserves timber and imported ironwork while retaining cartwright and construction support, and new workshops default to one six-person company's reserve. Carpenters issue only one weapon per assigned guard and keep surplus at the workshop, so an inactive or partial company no longer drains an entire armory. Unarmed companies also do not warehouse provisions they cannot consume. Every armed company can hold a lean, standard, or deep ration reserve of 3, 6, or 12 food per guard; existing saves retain the former six-unit target. Lean policy releases perishable food and carts to households, while a deep reserve can bridge a disrupted frontier route at the cost of spoilage exposure and a larger plunderable stock. Their routine provision carts take only stock above local household delivery reserves, while any assigned granary hauler can source-dispatch an emergency cart to the armed company with the lowest food runway once it drops below three days. If grain processing is also critical, the lower relative runway wins before route distance and stable building order. Military upkeep therefore creates a real surplus-production and cart-capacity requirement instead of silently starving the nearest homes. Warning coverage improves their ability to muster, and rain or cold-season ground conditions make long watch routes respond as if they were farther away, so lookout placement, road layout, seasonal planning, and guard upkeep reinforce each other instead of becoming separate combat systems.
- **Palisaded refuge** — after completing a guardhouse, a contested settlement can invest 72 physically hauled timber and 30 stone in a compact wooden-and-earth civilian enclosure. Building inventories, loaded carts, workshops, and Town Hall treasury remain exposed where they are physically stored, so the refuge cannot teleport a granary into safety or replace paid guards. - **Road-matched specialty export ledger** — the Town Hall follows physical ale, wine, honey, cheese, cloth, and pottery from completed producers through loaded carts into each Trading Post queue. Cached road branches expose source stock with no completed route, full destination stores, unstaffed or fire-blocked producers, returning source carts, and occupied receiving slots. The broker side evaluates drink, provision, and wares policies against their own rates, so one eligible family can sell while another remains held. - **Road-matched armament ledger** — in contested worlds the Town Hall now audits the whole imported-ironwork → carpenter → guardhouse chain by cached road component instead of treating every owned weapon as interchangeable. Winter herds consume that hay before emergency grain. ### Residences

- **Residence zone placement** — click two points along a road for the frontage edge, then place two independent back corners to shape the angled rear boundary; the free-form quadrilateral subdivides into residence parcels.

Tier 2 adds ale, clothing, and two distinct food categories while retaining that basic-church standard; Tier 3 introduces the level-2 stone-church standard and requires a balanced pantry with at least one stocked crops/forage category, one meat/animal-produce category, and fish. Tier 4 adds preserved food, slowly replaced pottery, physical fired roof tiles, a viable market or household luxury source, and a level-3 church standard while retaining every lower-tier service. A category counts only when the household holds at least one household-day of it, and close substitutes combine within their category. A water route must fall inside the well's physical service radius as well as share a road branch, preventing upgrades into homes that can never receive water.

- **Procedural residence meshes** — a deliberately shorter Tier 1 cottage uses a thick bundled-thatch roof, Tiers 2 and 3 grow into two-storey houses with split wooden shingles, and Tier 4 gains expanded massing, dressed stonework, a central cross-gable, and fired clay tiles. Each deterministic model exposes its tier, massing modules, façade modules, and roof finish as one authored building plan; instanced fence posts and rails remain along zone boundaries.
- **Residence needs** — residents consume firewood, water, and food per person per tick; homes track per-need stock and deficit timers server-side.
- **Persistent housing & satisfaction** — shortage never abandons a residence. Empty population slots remain available to new settlers; sustained unmet needs lower settlement approval after a grace period and then block further promotion until service recovers. Household labor and housing remain unchanged; sustained Tier-4 non-vital shortages only trim optional purchases and their related local market tax by 25%.
- **Backyard extensions** — click an occupied home's backyard, choose the extension explicitly, then place it inside the free-form parcel. New plots offer an apple orchard, vegetable garden, flower bed, herb plot, hen yard, goat pen, or small apiary; the former cherry orchard remains loadable in old saves but is hidden from new placement. Food extensions supply their own household first, then the Granary assigned to the nearest staffed food-stall group accepts configured surplus as typed provisions. The Granary may send honey or fruit to a selected Brewhouse before a worker physically restocks household stalls; once Honey reaches a Marketplace it can satisfy Food or Tier-4 Luxury comfort. Without a compatible Granary worker or storage room, rejected food stays with the producing household as pantry space permits. Herb remedies enter the assigned Storehouse before a goods-stall cart; goat hides use an independent Storehouse assignment and remain there until a Tannery or Trading Post accepts them. Neither materializes directly at the square. Small apiaries provide less honey and pollination than the specialist Apiary. Flowers earn no passive coin. Output follows the 06:00–20:00 workday, seasonal windows, drought, and an observed Sunday Sabbath. No backyard inventory is auto-exported.
- **Food variety by category and diet group** — the pantry keeps physical commodities. Tier 2 counts distinct categories: grains, vegetables, fruits, animal produce, meats, fish, foraged foods, and honey. Tier 3 instead requires all three broad diet groups—crops/forage, meat/animal produce, and fish—so three crop rows cannot fake a balanced diet. Multiple vegetable visuals remain one Vegetables commodity; apples and legacy cherries are both Fruit, while milk, cheese, and eggs are Animal Produce. Market delivery selection first fills a missing Tier 3 diet group, then prefers a missing category, so variety emerges from the physical distribution system rather than item-count inflation.
- **Household economy** — each occupied home tracks capped savings. A successfully staffed backyard sale credits seller wealth and assesses one local market levy; routine internal demand is aggregated rather than debiting individual buyer purses, so the same food system does not punish poor households or manufacture thousands of tiny coin trips. The levy remains physical in the Marketplace until a free hauler reaches the civic treasury. Emergency regional orders at a Trading Post still debit the ordering household, and parish tithes remain a separate later outflow. Residence, backyard, City Administration, and Town Hall views expose those distinctions and the 120-day seasonal/stall outlook.
- **Residence inspector** — abstractly allocated firewood/water/food stock, runway days, household wealth, serving Marketplace/well, upgrade readiness and blockers, chapel link, road access, settlers pending, and demolish options for a single home or entire zone. Connected homes share the stock at their nearest compatible distribution point; exact route distance and stable plot order decide scarce availability.

## SpacetimeDB (authoritative backend)

This project uses [SpacetimeDB 2.0.1](https://spacetimedb.com/) for authoritative game state: treasury, buildings, trees, quarries, foraging nodes, roads, residence zones, backyard gardens, delivery trips, and the full settlement supply chain. The client is a thin renderer — all economy simulation runs in the Rust module via a scheduled `tick_sim` reducer every 200 ms.

### Backend commands

Publish the Rust module and regenerate TypeScript bindings:

```bash
npm run deploy:local
```

This runs `generate:world-bootstrap` (tree and foraging layout data for server bootstrap), `generate:game-balance` (shared economy constants), publishes the module to database `city-builder`, and writes TypeScript bindings to `src/generated/`.

To wipe and republish from scratch:

```bash
npm run deploy:local-clean
```

The client connects to `http://localhost:3000` with database name `city-builder`.

### Anonymous identity

No login is required for local dev. On first connect SpacetimeDB issues a signed JWT; the client stores that token in `localStorage` (keyed by database name) and reconnects with the same player identity on refresh. Treasury, buildings, roads, and residences are scoped to that identity.

When real auth is added later, swap the token source in `src/network/identityPersistence.ts` — the connection layer stays the same.

### Server connection required

Medieval Settlement is **not playable without a live SpacetimeDB connection**. The client renders replicated server state; it does not queue roads, buildings, or economy actions offline.

- **Boot** — the loading screen stays up until SpacetimeDB connects, subscribes, and world bootstrap completes. If the server is down, you get a retry screen instead of partial gameplay.
- **Mid-session disconnect** — all construction tools are disabled and a reconnect overlay appears with automatic retry.
- **New world** — requires a live connection; `reset_world` must succeed on the server before local settings and identity are cleared.

See `docs/design/server-authoritative-connection.md` for the full connection model.

## How It Works

The terrain is generated as a continuous heightfield in `src/terrain/Terrain.ts`. It combines several value-noise layers with broad sine/cosine shaping, then uses vertex colors to blend grass tints and a shore-blend attribute for muddy river banks. `TerrainGrassMaterial.ts` builds a TSL node material that samples meadow, dense, and dry PBR sets per vertex.

`RiverLayout.ts` generates procedural river corridors from map edges toward a central drain, with optional tributaries. `RiverField.ts` rasterizes those corridors into mask and signed-distance fields used for terrain carving, shore mud blending, and prop blocking. `RiverWaterMesh.ts` runs a lightweight 2D virtual-pipes water simulation each frame and drives animated foam and shore effects through `RiverWaterMaterial.ts`. `HydrologyOverlay.ts` reuses the river field to visualize groundwater scores for well placement.

`QuarryLayout.ts`, `MineralDepositLayout.ts`, and `ClayDepositLayout.ts` place the physical geological rolls. Every deposit exposes a finite surface reserve for a nearby Mining Pit; rich deposits additionally support a centered Quarry whose underground source does not deplete. Quarry timber supports are road-hauled from a lumber mill or village storehouse and are consumed by completed underground batches. Geological and wild-resource nodes (game, berries, mushrooms, and water-bound fish shoals) share the fixed 5 / 20 / 40 size budget and its exact 2 / 8 / 16 rich grades. The generator guarantees at least 1 / 4 / 8 game, berry, or mushroom nodes, then abundance and seed can roll additional wild-food sites; fish may supplement but never replace that floor. A separate seeded pass assigns the rich grades across the complete node roster, so game, berries, mushrooms, and fish can all be ordinary or rich. `resourceRegionDistribution.ts` gives every small-map-sized territory a baseline share of the map's nodes and rolls the remainder between territories; each layout treats those positions as preferences rather than hard borders, preserving valid riverbank clay, water-bound fish, forest forage, dry quarries, and mineral formations. A tight regional roll can omit a geological family, so the Trading Post remains the fallback for missing local stone, clay, iron, or salt. Generated nodes are bootstrapped from `world_foraging.json`; `foraging_respawn.rs` advances their persistent lifecycle rather than deleting or rerolling them. Berry fruit and close-zoom mushroom models vanish as stock is gathered and return in the growing season; deer actors disappear one-for-one as hunters kill them and move with a migrating habitat.

Road placement is handled by `src/roads/RoadTool.ts`. Pointer input is projected onto the terrain by `TerrainProjector`, collected as clicked road nodes with optional wheel-adjusted curvature, validated against slope and minimum length rules, and committed into a `RoadNetwork`.

`src/roads/RoadNetwork.ts` stores roads as nodes and edges. It resolves endpoint snapping, splits existing road segments when new paths connect into them, detects crossings, prunes orphan nodes, and classifies junction types.

`src/roads/RoadMeshBuilder.ts` turns road graph edges into terrain-following ribbon meshes. It samples Catmull-Rom curves, builds a core dirt ribbon, adds irregular blended shoulders, and keeps the road slightly above the terrain to avoid z-fighting. When a path crosses water, `RiverBridgeSpans.ts` detects wet runs, raises the deck above the water surface, and blends graded approach ramps; `BridgeSupports.ts` places instanced posts under the deck. `RoadJunctionBuilder.ts` adds endpoint caps and junction patch geometry at classified nodes.

`RoadPlacementValidation.ts` checks slope, minimum length, max bridge span, and rock collisions before commit. `RiverShoreCrossingGaps.ts` seeds procedural clearance zones along river banks so shore stones skip natural crossing points.

`src/props/ForestProps.ts`, `ForestUndergrowth.ts`, and `ForestManager.ts` scatter instanced conifer trees, bushes, ferns, and rocks across the playable area. Roads automatically clear trees and undergrowth but remain blocked by loose boulders, preserving meaningful route planning. Building pads and farm fields prepare their sites by clearing vegetation and overlapping loose rocks; construction also deletes tree entities inside the authoritative building footprint without granting free timber. `RoadStumps.ts` places cut stumps along road shoulders after clearance. `RiverReeds.ts` adds instanced reed clusters along river banks. `ForestVisualSync.ts` mirrors server tree phases (`stump`, `growing`, `mature`) onto the instanced forest — growing trees swap to animated sapling meshes via `TreeSaplings.ts`.

`src/buildings/BuildingTool.ts` handles placement of all production, faith, and trade buildings. `BuildingPlacementValidation.ts` rejects water, unsuitable slopes, overlapping footprints, and missing local natural resources where a building fundamentally depends on its site. Shore buildings use dense bank sampling so narrow rivers are recognized reliably. Placement creates an inert construction site: `ConstructionSiteMesh.ts` stages foundations, scaffolding, frames, and material piles while `server/src/simulation/construction.rs` reserves spendable stock, lets unassigned labor fetch it from any completed reachable source, prefers organized storehouses as pickup locations without borrowing their workers, handles the founding reserve, and gates builder progress by delivered materials. Road access is not a placement prerequisite, so a waiting site can be connected afterward.

`src/residences/` handles residence zone drawing — a frontage edge snapped to the road network plus a depth point defining the rectangular plot. Layout and placement validation subdivide the zone into residence parcels and enforce road frontage, depth limits, overlap checks, and resource costs. `ResidenceMarkers.ts` and parcel fencing render procedural houses along zone boundaries. Placement calls the residence-zone reducer; the server creates residence rows with population capacity scaled by parcel width. `residence_settlement.rs` gradually fills homes; `backyard_garden.rs` runs garden production and treasury tax.

`src/logistics/` mirrors server distribution and hauling logic on the client for inspector displays — runway days, market/well territory, physical trip durations, and residence needs status. The server batches exact road-distance claims, allocates scarce market and well stock to the nearest connected homes, and reserves no labor for routine last-mile supply. Industrial water remains physical: processors consume only water unloaded into their own store, while inspectors show inbound carts and stored cycle coverage. `DeliveryAgentRenderer.ts` animates genuine `delivery_trip` rows as wooden carts along the road network, with rigged villagers walking at the handles and keeping their hands planted through a lightweight IK pass. `src/roads/roadConnectivity.ts` and `server/src/roads/network.rs` compute Dijkstra road-path distances for building access, distribution priority, and supplier routing.

`src/placement/` maintains a spatial index of building, residence zone, and road footprints for fast overlap checks during placement.

`src/grass/GrassBladeField.ts` streams instanced 3D grass tufts in camera-relative chunks. Tufts fade in at close zoom (aligned with the terrain dirt LOD band) and are cleared near committed roads. `TerrainRoadWear.ts` updates a per-vertex `roadWearBlend` attribute so the TSL grass material tints to packed dirt along road corridors.

`src/data/spacetimeGameStore.ts` subscribes to replicated tables and maps rows into client `GameState`. Before the scene exists, startup probes `world_config` and adopts any configured server generation contract; browser storage is only a fallback when that probe is unavailable. `GameRuntime.ts` then connects, verifies that the finished terrain still matches the current server row, publishes settings for a new world via `configure_world`, bootstraps quarries, trees, and foraging from the client layout, and hydrates the road network from the server snapshot. A late authority race is surfaced once and requires a reload instead of retrying every replicated tick. Module `init` still seeds deploy-time embedded JSON so a fresh publish has world entities before the first client connects; `bootstrap_*` reducers apply client-authored rows only and no longer fall back to that JSON when empty arrays are sent. `reset_world` clears settlement progress and global entities but does not re-seed deploy-time defaults — the next connect re-publishes settings and re-bootstraps from the authoritative layout.

On the server, `server/src/reducers/simulation.rs` runs each 200 ms tick: construction reservations/hauling/builder work, wild-resource lifecycle and habitat migration, lumber mills, reforesters, quarries, lodges, wells, hunter's halls, forager's sheds, fishing camps, the grain→food processing chain (fields, barn, watermill, granary, brewery, smokehouse, apiary, vineyard), monastery estate production/reinvestment/hospitality/pilgrimages, market-imported iron, charcoal-fired smithing, physical civilian-tool maintenance, carpenter polearms, guardhouse readiness/upkeep, `delivery_trips.rs` road agents, progressively tier-gated residence needs, backyard gardens, chapel tithes, household discretionary trade, and settlement growth. Fresh food is physically held by producer buildings, homes, smokehouses, monasteries, marketplaces, granaries, and guardhouses and spoils continuously according to season, weather, and storage quality. Staffed Granaries and Storehouses physically replenish Marketplace stalls; the market then allocates routine food, preserved food, ale, firewood, cloth, and pottery to road-connected homes without creating delivery trips. Wells do the same for connected homes inside their service radius. Per-owner, per-need claims are built lazily, use exact road distances, and give scarce stock to the nearest households first. Paid emergency orders, remedy care, industrial water and fuel, institutional supply, tax collection, and inter-building logistics remain physical. Cached food-territory counts protect local household and producer-policy reserves before any institutional pull or producer-pushed cart is loaded. Apiaries protect their selected winter honey floor before monastery hospitality and Trading Post dispatch; vineyards harvest grapes, protect the selected table reserve, and ferment only complete staffed batches before wine hospitality and export. Policy reads are cached once per owner and simulation substep. Smokehouses receive granary stock only through the granary's selected household/preservation order, while armed guardhouses below their three-day floor enter the same source-side critical-cart arbitration as starved grain processors; this removes building-iteration order from central food policy. Farm seed protection performs one owner-wide field pass per simulation substep and updates the affected holding after field work. Seed distribution then scans short holdings once per free granary or staffed market, picks one least-covered road-reachable claim without sorting the branch, and rejects destinations already receiving grain; the work therefore scales with actual seed sources instead of repeating a source search from every farmstead. A lazy per-tick owner/building-kind index supplies construction-material, grain, guard, processor, market, parish, firewood, water, and territory candidate rosters from one building-table pass per substep. Construction receives the initially stocked source IDs—material stock can only shrink during that phase—and every candidate ID is resolved through the primary key before selection, preserving current stock, staffing, completion, fire, and inbound-cart state. Sunday schedule checks share one indexed Sabbath-policy read and one derived staffed-chapel result per owner and substep instead of repeatedly scanning the whole settlement; chapel completion invalidates that owner’s derived result before later phases. Immutable road snapshots are parsed and indexed once per scheduler heartbeat, then shared by delivery movement and every economy substep while their mutable caches remain isolated. Idle fire ignition combines five exact per-tick probabilities into one one-second structure scan; burning, damage, response, and spread still advance every substep, using one occupied-target set instead of repeated incident queries. The remaining economy shares one lazy disabled-target set, while chapel and monastery IDs ride the normal building classification pass instead of triggering two more whole-table scans. Labor reconciliation runs only when population is actually removed; a returning owner receives one connection-time repair for legacy or interrupted saves instead of paying a settlement-wide allocation scan on every economy substep. Unstaffed processors neither request inputs nor dispatch provision carts. Incomplete or fire-disabled buildings are excluded from production, services, bonuses, trade, and policy gates. Economy constants come from `balance/gameBalance.json` via `balance_generated.rs`.

`src/resources/ResourceInspector.ts` provides the settlement HUD and click-to-inspect panel for quarries, foraging nodes, buildings, residences, backyards, and river access — including labor assignment, grain-work priority, demolish actions, hydrology grades, and delivery status. `WorldQueries.ts` resolves inspectable targets from terrain clicks. `src/map/` projects quarry, foraging, and backyard icons at zoomed-out camera levels.

`src/camera/CameraController.ts` drives the RTS orbit camera with smooth pan, rotate, and zoom (displayed as a percentage in the HUD). `FirstPersonController.ts` handles walk mode — pointer-lock look, terrain- and road-deck-sampled foot placement, sprint/jump/crouch, free-look, camera bob, and compass heading publication.

`src/ui/BuildToolbar.ts` composes the construction dock, illustrated build menu, settlement HUD, contextual tip cards, FPS/zoom stats, compass strip, residence layout HUD, delete popup, and game menu. `ToastManager.ts` surfaces placement validation errors. `LoadingScreen.ts` shows staged progress during world bootstrap. `AmbientAudioController.ts` crossfades wind and village ambience based on camera distance to your buildings and residence zones.

`src/scene/SceneManager.ts` owns the renderer backend, terrain, sky, forest, grass field, river system, quarry system, hydrology overlay, road groups, delivery agents, selection/preview groups, lighting, fog, and post-processing. Forest and grass build asynchronously after the first frame to keep initial load responsive.

## Development Notes

- Road editing works offline; buildings, residences, and economy require a running SpacetimeDB server (`pnpm run dev` + `pnpm run deploy:local`).
- `npm run build` runs TypeScript first, then Vite's production build.
- `npm run deploy:local` regenerates world bootstrap data and game-balance constants, publishes the Rust module, and refreshes `src/generated/` bindings — run this after any server schema, reducer, or balance change.
- `npm run generate:game-balance` regenerates `server/src/balance_generated.rs` and `src/generated/gameBalance.ts` from `balance/gameBalance.json`.
- `npm run test` / `npm run test:ci` run the TypeScript contract-test suite (`scripts/run-all-tests.mts`).
- `cargo test` in `server/logic/` runs host-side Rust unit tests for pure simulation/economy logic. The WASM module crate itself cannot link native `cargo test` binaries.
- `pnpm run test:e2e` / `pnpm run smoketest` run the Playwright smoke path: connect to SpacetimeDB, open the build menu, place a reforester, and assert the settlement HUD timber drops. Requires a running database (`pnpm run dev` or `pnpm run dev:db`), a published `city-builder` database (`pnpm run deploy:local`), and Playwright Chromium (`pnpm exec playwright install chromium`).
- GitHub Actions CI runs contract tests, client build, `cargo check`, `cargo test`, and the browser smoke job against a local SpacetimeDB instance.
- `npm run test:lodge-logistics` runs a standalone script validating firewood delivery routing logic.
- `npm run test:fishing` validates fish world placement, dry-land camp placement, storage, residence food claims, icon treatment, finite population harvesting, protected-stock caps, spring reproduction, winter freeze, extinction, population-scaled school visuals, and the rigged swimming/flop animation asset.
- `npm run test:foraging-ecology` validates mushroom world placement and deep-forest bias, seasonal policy, forager compatibility, wild-stock reserve parity, persistent lifecycle wiring, herd visuals/migration, and granary collection.
- WebGPU is attempted first; if initialization fails or the browser lacks support, the app falls back to WebGL automatically.
- Production build splits Three.js, SpacetimeDB bindings, and vendored vegetation/sky code into separate chunks to keep the main entry bundle smaller.
- Forest and grass vegetation build asynchronously after the first frame to keep initial load responsive.
- `window.__medievalGameState` exposes dev helpers for inspecting live client state in the browser console.
- `dist/`, `node_modules/`, logs, and local editor files are ignored by Git.
